## 1. 제안 요지

이 제품의 품질은 "AR이 되느냐"가 아니라 **안경이 얼굴 위 정확한 위치에 얹혀 있느냐**에서 갈린다. 얼굴 추적 자체는 무료 라이브러리로 해결되는 영역이고, 경쟁력은 그 출력을 받아 **코 패드가 콧대에 닿는 깊이를 정하고, 다리가 관자놀이를 파고들지 않게 벌리고, 렌즈가 각막에서 적절한 거리를 유지하도록 만드는 정합 로직**에 있다.

따라서 제안의 중심은 라이브러리 선정이 아니라 **정합 엔진의 설계와 그것을 수치로 검증하는 체계**다. 이 엔진은 이미 동작하며, 얼굴 변형 14종 × 포즈 5종 = 70 케이스를 Blender 실메시 판정으로 통과한 상태다(§5).

## 2. 기술 스택과 선정 근거

| 계층 | 채택 | 선정 근거 | 검토 후 배제 |
|---|---|---|---|
| 얼굴 추적 | **MediaPipe Face Landmarker** (`@mediapipe/tasks-vision`) | 무료·온디바이스(영상 미전송). 웹과 안드로이드 Tasks API의 **출력 구조가 동일**해 공용 코어가 1:1로 대응. 홍채 랜드마크 제공 → PD 측정 가능 | 구 `@mediapipe/face_mesh`: 변환 행렬 미제공 · TF.js `face-landmarks-detection`: 성능 미달 · 상용 SDK(Jeeliz·Banuba·DeepAR·8th Wall): 라이선스 비용 |
| 3D 렌더 | **Three.js (WebGL2)** + GLTFLoader | 검증된 GLB 파이프라인, 깊이 전용 오클루더·노드 리깅을 표준 기능으로 처리. 대안 대비 학습·유지보수 비용 최저 | Babylon.js: 기능 과잉 · 생 WebGL: 개발량 과다 |
| AR 런타임 | **사용 안 함 — 직접 카메라 정합** | WebXR은 얼굴 추적 API를 표준화하지 않았고, 브라우저 지원이 제한적. MediaPipe 가상 카메라(수직 FOV 63°)와 Three.js 투영 행렬을 직접 일치시키는 편이 정확하고 호환 범위가 넓다 | WebXR Device API · ARCore Augmented Faces(§부록 A 참조) |
| 언어·빌드 | **TypeScript + Vite** | 공용 코어의 타입 안정성, 안드로이드 Kotlin 이식 시 인터페이스 대응이 명시적 | — |
| 카드 검출 | **OpenCV.js** (카드 캘리브레이션 한정) | ISO ID-1 카드 사각형 검출에만 사용, 지연 로드로 초기 로딩 영향 없음 | — |
| 안드로이드 | **WebView 하이브리드 셸** | 예산·일정 제약 하에서 "안드로이드 앱 + 웹 동시 동작" 요구를 충족. 상세 근거는 §부록 A | Kotlin 네이티브(Phase 2) · TWA(오프라인 불가) |

> **ARCore를 쓰지 않는 이유**는 부록 A에 따로 적었다. Augmented Faces는 홍채 랜드마크를 제공하지 않아 **PD 측정(RFP 과업 2-3)이 성립하지 않는다.**

## 4. 공용 코어 설계 — RFP 우대사항 대응

RFP는 "안드로이드/웹 간 핵심 로직을 공용 모듈로 설계하여 중복 개발 최소화, 플랫폼별 렌더링/카메라 계층은 분리 구현"을 요구한다. 그 요구를 코드 구조로 이미 만족시켰다.

| 원칙 | 구현 |
|---|---|
| 순수 함수 | `FittingCore.process(FrameInput) → FitOutput` 하나가 진입점. 전역 상태·DOM·WebGL 접근 없음 |
| 인터페이스 고정 | 입력은 `landmarks[478] · matrix[16] · blendshapes`, 출력은 `glassesMatrix · angles · scale · pd · clearance` |
| 하드코딩 금지 | 랜드마크 인덱스 집합(측두부 정점, 코·눈썹·볼 삼각형)을 정규 모델 기하 조건에서 **런타임에 계산** — 모델이 바뀌어도 자동 추종 |
| 이식 대비 | [`docs/core-interface.md`](../core-interface.md)에 TypeScript ↔ Kotlin 타입 매핑표를 유지 |
| 등가성 검증 | **골든 벡터** — 입력 시퀀스와 기대 출력을 JSON으로 고정. 이식 구현은 같은 벡터를 허용 오차(이동 0.5 mm, 회전 0.2°, PD 0.2 mm) 내로 재현해야 통과 |

골든 벡터가 이 설계의 핵심이다. Phase 2에서 Kotlin 코어를 작성할 때 "웹과 같게 동작하는가"를 **사람 눈이 아니라 테스트로** 판정할 수 있게 한다.

## 5. 정합 엔진 — 제품 품질을 만드는 부분

RFP의 "프레임 3D 모델 정합(얼굴 크기/각도에 따른 자동 스케일링/회전)"은 한 문장이지만, 실제로는 다섯 단계다.

| 단계 | 방법 | 해결하는 문제 |
|---|---|---|
| 1. 메트릭 복원 | 정규화 랜드마크를 카메라 공간 mm로 역투영. 깊이는 **하이브리드** — 눈·눈썹·볼·측면은 정규 모델 깊이(안정), 코 영역만 개인 랜드마크 z를 눈 기준으로 정렬해 반영 | 정규 모델 깊이만 쓰면 고개를 돌릴 때 프레임이 4 mm 미끄러짐 → 2 mm 이내로 감소 |
| 2. 스케일 | 관자놀이 폭 60 % + 눈 외각 폭 40 % 가중 비율. PD 확보 시 홍채 mm 기준 실치수 모드 | 얼굴 크기에 맞는 실제 비율 |
| 3. 코 착지 | 에셋의 **코 패드 접촉점**을 코 옆면 삼각형 높이장에 얹어 깊이 결정 | 능선 기준으로 얹으면 처음부터 5~8 mm 앞에 뜸 |
| 4. 클리어런스 | 림 외곽선·브릿지 바·패드 프로브를 눈썹·볼·코 높이장과 비교해 전방 보정. 측두부 정점 띠로 다리 벌림(0~15°). **정점간 거리(렌즈 뒷면–각막)를 10~23 mm로 클램프** | 얼굴 관통과 부유를 동시에 방지 |
| 5. 오클루전 | 478점 깊이 전용 얼굴 메시 + 두개골·귀 프록시 메시 선행 렌더 | 먼 쪽 다리가 실루엣 밖으로 삐져나오는 현상 제거 |

### 5.1 현재 측정값

| 지표 | 수정 전 | 현재 | 목표 |
|---|---|---|---|
| 정점간 거리(렌즈 뒷면–각막) | 27~35 mm | **15.9~23.0 mm** | 실제 안경 12~15 mm |
| 전방 보정 | 10.0 mm | **≤ 8.0 mm** | 작을수록 좋음 |
| 관통 잔여 (다리/눈썹/볼) | −0.98 mm(관통) | **−2.5 / ≤ −4.1 / ≤ −2.5 mm** | 모두 ≤ 0 |
| 고개 돌릴 때 깊이 미끄러짐 | 4 mm | **≤ 2 mm** | 작을수록 좋음 |
| Blender 실메시 판정 | — | **70/70 통과** | 전수 통과 |
| 코어 자동 테스트 | — | **14 파일 / 91 테스트 통과** | 전수 통과 |

검증 근거: [`docs/verification/2026-09-08-float-fix.md`](../verification/2026-09-08-float-fix.md), [`docs/verification/2026-09-08-fit-bench.md`](../verification/2026-09-08-fit-bench.md)

> **아직 측정되지 않은 것**: 실기기 FPS, 실착용 사진 대비 브릿지 착지 오차, 피험자 기준 PD 오차. 위 수치는 합성 얼굴 변형과 Blender 실메시 기준이다. 실측은 [05 일정](05-일정-마일스톤.md) W5·W9에 배치했다.

## 6. 검증 체계

품질을 주장이 아니라 **재현 가능한 수치**로 남기는 것이 이 제안의 차별점이다.

| 도구 | 용도 |
|---|---|
| 디버그 HUD | 정점간 거리·패드 간격·관통 잔여·전방 보정·지터·지연·FPS를 실시간 계기로 표시 |
| 세션 녹화·재생 | 랜드마크 시퀀스를 JSON으로 저장 → 같은 입력으로 필터 파라미터 회귀 비교 |
| 지표 CSV | 프레임별 전 지표를 내보내 통계 분석 |
| 골든 벡터 | 입력 + 기대 출력 고정, 플랫폼 간 등가성 판정 |
| 얼굴 변형 벤치 | 14종 얼굴 × 5 포즈 자동 실행, 관통·부유 수치 산출 |
| Blender 실메시 판정 | 실제 GLB 메시 대 얼굴 메시 BVH 부호 거리 계산 + 렌더 이미지 |

이 체계 덕분에 "자연스러워 보이나요?"를 "정점간 거리 18.2 mm, 관통 잔여 −2.1 mm"로 바꿔 논의할 수 있다.

## 부록 A. 안드로이드 구현 방식 비교 — 네이티브 vs WebView

### A.1 기술 비교

| 항목 | 네이티브 (Kotlin) | **WebView 하이브리드 (제안)** | TWA |
|---|---|---|---|
| 추적 엔진 | MediaPipe Tasks Android — 웹과 출력 구조 동일 | 웹 코드 그대로 | 웹 코드 그대로 |
| ARCore Augmented Faces 대안 | **불가** — 홍채 랜드마크·블렌드셰이프 미제공으로 PD 측정과 깜빡임 게이팅이 성립하지 않음. Play Services for AR 의존 추가 | 해당 없음 | 해당 없음 |
| 렌더링 | Filament / SceneView / GLES 직접 구현 | Three.js WebGL2 — **이미 동작** | 동일 |
| 카메라 제어 | CameraX — 노출·포커스 락 가능 | `getUserMedia` — 제어 불가 | 동일 |
| 오프라인 기동 | 가능 | 가능 (자산 앱 번들) | **불가** (원격 HTTPS 필수) |
| RFP "네이티브" 문구 부합 | 완전 부합 | 해석·합의 필요 | 미부합 |

### A.2 공수 — 현재 코드베이스 실측 기준

| 구간 | 현재 상태 | 네이티브 추가 | WebView 추가 |
|---|---|---|---|
| 공용 코어 (순수 로직) | TypeScript 2,674줄 구현됨 | Kotlin 1:1 이식 + 골든 러너 **8~12 md** | **0 md** |
| 렌더링 계층 | Three.js 1,908줄 (GLB 리그, 478점 오클루더, 두개골 프록시, 틸트·벌림) | Filament/GLES 재작성 **15~20 md** | **0 md** |
| 카메라 계층 | `getUserMedia` + `requestVideoFrameCallback` | CameraX + 텍스처 파이프라인 **4~6 md** | **0 md** |
| 앱 셸 | — | (위 포함) | 권한·전체화면·번들·스토어 **4~6 md** |
| **소계** | | **27~38 md** | **4~6 md** |

공통 작업(웹 제품화 20~25 md, PD 실측 튜닝 5 md, API 문서 3 md)을 더하면:

| 방식 | 총 공수 | 47 영업일 내 1인 완수 |
|---|---|---|
| 네이티브 병행 | 55~71 md | **불가** (8~24일 초과) |
| **WebView 하이브리드** | **32~39 md** | **가능** (여유 8~15일) |

**네이티브 병행이 성립하지 않는 이유는 예산이 아니라 일정이다.** 인원을 늘려 일정을 맞추면 예산 제약(최대 700만 원)에서 단가가 md당 10만 원 수준이 되어 더 나빠진다.

### A.3 Phase 2 전환 경로

WebView 선택은 네이티브 포기가 아니라 **연기**다. 전환에 필요한 자산은 Phase 1에서 이미 만들어진다.

| Phase 2 작업 | Phase 1에서 준비되는 것 |
|---|---|
| Kotlin 코어 작성 | 순수 TS 코어 2,674줄 + [`core-interface.md`](../core-interface.md) 타입 매핑표 |
| 코어 등가성 검증 | 골든 벡터 체계 — 통과 기준이 이미 정의됨 |
| 네이티브 렌더러 | GLB 규격서 + 앵커 메타 + Blender 판정 도구 |
| 정합 파라미터 | Phase 1 실측으로 확정된 설정값 그대로 이식 |

즉 Phase 2는 "다시 만들기"가 아니라 **"검증 기준이 이미 있는 상태에서 옮기기"**가 된다.
