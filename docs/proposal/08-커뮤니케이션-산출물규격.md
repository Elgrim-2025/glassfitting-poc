## 1. 채널

당사 제안이며, 발주사 환경에 맞춰 조정 가능하다. **중요한 것은 도구 종류가 아니라 "결정이 어디에 기록되는가"다.**

| 용도 | 제안 | 대안 | 비고 |
|---|---|---|---|
| 버전 관리 | **Git + GitHub (비공개 저장소)** | GitLab, 발주사 자체 저장소 | 산출물인 소스 코드 원본이 여기에 쌓인다 |
| 이슈·범위 변경 | **GitHub Issues** | Jira, 트렐로 | **범위 변경은 반드시 이 채널에 기록된 시점부터 유효** |
| 일상 소통 | **카카오톡 또는 슬랙** | 이메일 | 구두·메신저 합의는 이슈로 승격해야 효력 발생 |
| 문서 공유 | **Git 저장소 내 마크다운** | 구글 드라이브 | 코드와 같이 버전 관리 |
| 대용량 자료 (디자인·3D 에셋) | **구글 드라이브 또는 드롭박스** | — | 저장소에 넣지 않음 |
| 정기 회의 | **화상 회의 (주 1회)** | 대면 | 회의록은 이슈로 기록 |
| 계약·범위 변경 조율 | **위시켓 담당 매니저** | — | 미팅 중 범위가 바뀌어 일정·금액을 다시 정해야 하면 매니저가 조율한다. 계약서는 미팅에서 합의한 내용으로 작성된다 |

> ※ 미팅 확인: 발주사가 이미 쓰는 도구가 있으면 그쪽에 맞춘다. 특히 **이슈 트래커**는 범위 분쟁 방지의 핵심이므로 어느 도구든 하나로 통일해야 한다.

## 4. 코드 인수 기준

납품 시점에 아래가 모두 충족되어야 한다.

| 항목 | 기준 |
|---|---|
| 빌드 재현 | 새 환경에서 `npm install && npm run setup && npm run build`가 문서만 보고 성공 |
| 자동 테스트 | `npm test` 전수 통과 |
| 타입 검사 | `npm run typecheck` 오류 0 |
| 문서 | README에 구조·실행·검증 절차 기재 |
| 비밀정보 | 저장소에 API 키·토큰·개인정보 없음 |
| 라이선스 | 사용 오픈소스 목록과 라이선스 고지 포함 |

## 6. 정부 지원금 사업 관련

RFP에 **정부 지원금 사업(한도 700만 원)**으로 명시되어 있다. 지원금 정산에는 통상 아래가 요구되므로 착수 전에 확인이 필요하다.

| 항목 | 확인 사항 |
|---|---|
| 정산 서류 | 필요한 서류 양식과 제출 기한 |
| 검수 확인서 | 지정 양식 존재 여부 — 있다면 [06 검수 기준서](06-검수기준서.md)를 그 양식에 맞춰 재구성 |
| 산출물 요건 | 지원 사업이 요구하는 산출물이 RFP 명시분(소스 코드 원본)과 다른지 |
| 지급 구조 | 위시켓 대금보호 — 선금·잔금이 아니라 **산출물 기준 분할 결제**. 차수는 05 마일스톤(M1·M2·납품) 기준으로 제안 |
| 계약 구조 | 위시켓 안심계약은 클라이언트↔위시켓↔파트너 구조다. 지원금 정산에 필요한 계약서·세금계산서 발행 주체가 지원 사업 요건에 맞는지 |
| 사업 기간 | 11/25 납품이 사업 기간 종료일인지, 정산까지 포함한 날짜인지 |

> **11/25가 "정산 완료일"이라면 실제 개발 종료는 그보다 앞당겨져야 한다.** [05 일정](05-일정-마일스톤.md)은 11/25를 개발 납품일로 가정하고 작성했다.
