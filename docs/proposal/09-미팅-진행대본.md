## 3. 데모 설명 — 구현 관점 (4분, 기술 질문이 나오면 확장)

### 3.1 한 장 요약

> "얼굴 추적 자체는 무료 라이브러리(MediaPipe)로 해결되는 영역입니다. 품질이 갈리는 곳은 **그 출력을 받아서 안경을 어디에 얹을지 정하는 정합 로직**이고, 저는 거기에 시간을 썼습니다."

### 3.2 구조 — 왜 이렇게 나눴는가

| 계층 | 내용 | 클라이언트에게 주는 의미 |
|---|---|---|
| **공용 코어** (순수 TypeScript 2,674줄) | 정합·필터·상태기계·PD. 화면도 카메라도 모름 | 웹/안드로이드가 **같은 코드**를 돈다 → 두 번 만들지 않음 (RFP 우대사항) |
| 플랫폼 계층 (웹) | 카메라·Three.js 렌더·HUD | 브라우저 쪽만 갈아끼우면 됨 |
| 플랫폼 계층 (안드로이드) | WebView 셸 (권한·전체화면·오프라인 번들) | Phase 1 납품분 |
| 추적 엔진 | MediaPipe Face Landmarker (온디바이스) | 라이선스 비용 0, 영상 미전송 |

### 3.3 기술 선택 — 세 줄로 방어

| 질문받을 것 | 답 |
|---|---|
| "왜 ARCore/WebXR을 안 쓰나?" | **ARCore Augmented Faces는 홍채 랜드마크를 안 줍니다. 그러면 PD 측정(RFP 과업 2-3)이 성립하지 않습니다.** WebXR은 얼굴 추적을 표준화한 적이 없습니다 |
| "왜 상용 SDK(Banuba·DeepAR)를 안 쓰나?" | 라이선스 비용이 계속 나가고, 정합 로직을 우리가 못 고칩니다. 지금 보신 관통 방지·코 착지는 **우리가 고칠 수 있어야** 개선됩니다 |
| "그럼 뭐가 어렵나?" | 정합 5단계 — ①mm 복원 ②크기 ③코 착지 ④클리어런스 ⑤오클루전. 이 중 ③④가 "떠 보임/파고듦"을 가릅니다 |

### 3.4 숫자로 말하기 — 이게 차별점

> "'자연스러워 보이나요?'를 '정점간 거리 18mm, 관통 잔여 −2mm'로 바꿔서 논의할 수 있게 만들어 뒀습니다."

| 지표 | 개선 전 | **현재** | 목표 |
|---|---|---|---|
| 정점간 거리(렌즈 뒷면–각막) | 27~35 mm | **15.9~23.0 mm** | 실제 안경 12~15 mm |
| 관통 잔여 (다리/눈썹/볼) | −0.98 mm(관통) | **−2.5 / ≤−4.1 / ≤−2.5 mm** | 모두 ≤ 0 |
| 고개 돌릴 때 깊이 미끄러짐 | 4 mm | **≤ 2 mm** | 작을수록 좋음 |
| Blender 실메시 관통 판정 | — | **70/70 통과** (얼굴 14종 × 포즈 5종) | 전수 |
| 코어 자동 테스트 | — | **91개 통과** | 전수 |

**정직하게 덧붙일 것** (신뢰가 여기서 갈린다):
> "다만 이 수치는 **합성 얼굴과 Blender 기준**입니다. 실기기 FPS, 실제 착용 사진 대비 오차, 사람 대상 PD 오차는 **아직 측정 안 했습니다.** 그래서 계획의 W5·W8·W9에 실측을 박아뒀고, 그 결과를 검수 보고서로 제출합니다."

### 3.5 품질 관리 도구 (보여주면 좋음)

| 도구 | 한 줄 설명 |
|---|---|
| 디버그 HUD | 정점간 거리·관통 잔여·지터·지연·FPS 실시간 계기 |
| 세션 녹화·재생 | 같은 입력으로 파라미터 바꿔 회귀 비교 |
| 골든 벡터 | 입력+기대출력 고정 → **안드로이드 이식본이 웹과 같은지 테스트로 판정** |
| 얼굴 변형 벤치 | 14종 얼굴 × 5포즈 자동 실행 |
| Blender 실메시 판정 | 실제 3D 메시로 관통 여부 계산 + 렌더 |
