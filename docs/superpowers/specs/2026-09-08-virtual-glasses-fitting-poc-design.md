## 1. 개요

### 1.1 목적
발주사 RFP(안드로이드·웹 AI 가상 안경 피팅 솔루션)의 본 개발에 앞서, **제품 품질을 좌우하는 3가지 핵심 기술이 웹 환경에서 목표 수준으로 구현 가능한지**를 수치로 검증한다. PoC의 결론은 Go/No-Go 판정과 본 개발(안드로이드 이식 포함) 계획의 근거가 된다.

### 1.2 PoC의 성격
- **검증용 프로덕트**: 상용 완성도가 아니라 "가능한가 + 어느 수준까지"를 측정 가능한 지표로 확인한다.
- **집중 개발**: 3대 핵심 기술 외 요소(UI/UX, 커머스 연동, 렌더링 미관)는 판정 기준에서 제외하고 최소 구현한다.
- **버리지 않는 코드**: PoC 코드는 본 개발 골격으로 재사용한다(11/25 납품 일정 보호).

### 1.3 핵심 보완·집중 기술 (3대 검증 항목)
| # | 핵심 기술 | 정의 | 품질에 미치는 영향 |
|---|---|---|---|
| ① | **자연스러운 위치 (Placement)** | 프레임이 코와 관자놀이에 실제 착용처럼 얹히고, 얼굴 크기에 맞는 실제 비율로 보이는 것 | 첫인상, "합성 티" 여부 |
| ② | **부착·추종 (Attachment / Tracking)** | 고개를 돌리고 움직여도 떨림·지연·이탈 없이 프레임이 얼굴에 붙어 따라오는 것 | 몰입감, 사용 지속 시간 |
| ③ | **간이 PD 측정** | RGB 카메라만으로 동공간 거리를 참고 수준(±수 mm)으로 추정 | 실치수 기반 정합 보조 + 사용자 참고값 |

세 기술은 서로 맞물린다. ③에서 얻는 mm 스케일이 ①의 실치수 정합을 가능하게 하고, ①의 안정된 앵커가 ②의 추종 품질을 측정하는 기준이 된다.

### 1.4 범위
| 포함 | 제외 |

| 핵심 기술 | 검증 가설 | Go 기준(요약, 상세는 6장) |
|---|---|---|
| ① 위치 | MediaPipe 얼굴 변환 행렬 + 정규 얼굴 모델 기준 1회 리깅 + 사용자별 스케일 보정으로 실착용 사진과 근접한 위치를 얻을 수 있다 | 브릿지 착지 오차 ≤ 2 mm, 프레임 폭 비율 오차 ≤ 3 %, 자연스러움 평가 ≥ 4.0/5 |

## 3. 핵심 기술별 접근 방안

### 3.1 공통 기반 — MediaPipe Face Landmarker
| 항목 | 내용 |
|---|---|
| 라이브러리 | `@mediapipe/tasks-vision` **FaceLandmarker** (WASM + GPU delegate) |
| 사용 출력 | `faceLandmarks` 478점(468 + 홍채 10) · `facialTransformationMatrixes` 4×4 얼굴 변환 행렬 · `faceBlendshapes` 52종 |
| 선정 근거 | 무료·온디바이스(영상 미전송), 웹과 안드로이드 Tasks API가 **동일한 출력 구조** → 공용 코어 이식이 1:1로 대응 |
| 주의 | 구 `@mediapipe/face_mesh`(JS)는 변환 행렬을 제공하지 않으므로 Tasks API 채택 |
| 대안(보류) | TF.js `face-landmarks-detection`, 상용 SDK(Jeeliz·Banuba·DeepAR·8th Wall Face) — 성능 미달 시 벤치마크 후보 |

`facialTransformationMatrixes`는 MediaPipe **정규(canonical) 얼굴 모델**을 검출된 얼굴의 위치·자세로 옮기는 회전·이동 변환이다. 안경 3D 모델을 정규 모델 위에 한 번만 배치해 두면 런타임에는 행렬만 갱신해 "얼굴에 붙은" 움직임을 얻는다.

### 3.2 핵심 기술 ① — 자연스러운 위치 (Placement)
**문제 정의**: (a) 브릿지가 콧대 위 정확한 높이에, (b) 다리가 관자놀이를 지나 귀 방향으로, (c) 프레임 폭이 얼굴 폭과 실제 비율로, (d) 얼굴 뒤로 가려질 부분이 가려져야 한다.

**접근: "정규 모델 기준 1회 리깅 + 런타임 행렬 구동"**
| 단계 | 내용 |
|---|---|
| 1. 오프라인 리깅 | 정규 모델 위에 안경 GLB를 배치. 원점(브릿지 중심)을 콧대 상단 랜드마크(168/6) 부근에, 다리가 관자놀이(127/356) → 귀 앞(234/454) 방향을 지나도록 맞추고 오프셋을 에셋 메타(`anchor`)로 저장 |
| 2. 런타임 구동 | 얼굴 변환 행렬을 Three.js `Object3D.matrix`에 직접 적용(`matrixAutoUpdate = false`) |
| 3. 사용자별 스케일 보정 | 관자놀이 폭(127↔356)·눈 간격 등을 정규 모델 대비 비율로 계산해 폭(X) 스케일 보정. ③의 mm 스케일 확보 시 프레임 실치수를 mm 그대로 렌더하는 **실치수 모드** |
| 4. 코 착지 보정 | 콧대 능선(6, 197, 195) 깊이와 브릿지 폭으로 Y/Z 오프셋 조정. 코 패드 타입(고정/조절)별 착지 높이 프리셋 |
| 5. 오클루전 | 468점 테셀레이션 얼굴 메시를 **깊이 전용(colorWrite=false) 오클루더**로 먼저 렌더. 귀·측두부는 행렬에 부착한 **머리 근사체(타원체) 오클루더**로 보완 |
| 6. 카메라 정합 | MediaPipe 가상 카메라(수직 FOV 63°)와 Three.js `PerspectiveCamera` 일치, 전면 카메라 미러링을 비디오·랜드마크·렌더 전 구간에서 일관 적용 |
| 대안 경로 | 478점 ↔ 정규 모델 Kabsch 정합으로 자체 포즈 추정(눈·코·관자놀이 가중) |

**검증 방법**: 실착용 사진(정면·yaw 30°)과 가상 착용 화면 오버레이로 브릿지·힌지·렌즈 중심 위치 차이를 mm 환산. 피험자 주관 평가(5점 척도) 병행.

### 3.3 핵심 기술 ② — 부착·추종 (Attachment / Tracking Stability)
**문제 정의**: 지터·지연·이탈은 서로 상충한다 — 평활을 강하게 하면 지연이 커진다.

| 요소 | 내용 |
|---|---|
| 프레임 파이프라인 | `requestVideoFrameCallback` 기준으로 검출 → 정합 → 렌더를 한 프레임 안에 처리. Web Worker 분리는 검토 항목 |
| 시간 필터링 | 행렬을 T·Quaternion·S로 분해해 각각 **One-Euro 필터** 적용. 회전은 slerp 기반 |
| 신뢰도 게이팅·상태기계 | `Tracking / Degraded / Lost` 상태. Lost 시 마지막 포즈 N프레임 유지 후 페이드아웃, 재검출 히스테리시스 |
| 극단 포즈 | yaw ±45°, pitch ±30°, roll ±30°. 범위 밖은 Degraded + 정면 복귀 안내 |
| 부분 가림 | 신뢰도 하락 → 필터 강도 상향, 이전 포즈 유지 |
| 성능 프로파일 | 입력 해상도 × delegate × blendshapes 조합을 벤치마크로 자동 선택. 검출 프레임 스킵 시 보간 |

**검증 방법**: 녹화 영상 재생 모드로 필터 전/후 궤적 비교. 지터 = 정지 3초간 브릿지 앵커 화면 좌표 표준편차, 지연 = 상호상관 지연.

### 3.4 핵심 기술 ③ — 간이 PD 측정
| 단계 | 내용 |
|---|---|
| 1. 홍채 기준 스케일 | 홍채 수평 지름 ≈ 11.7 mm. 홍채 랜드마크(좌 468~472, 우 473~477)로 mm/px 산출 → 홍채 중심(468, 473) 거리 × 스케일 = PD |
| 2. 카드 기준(보조) | ISO ID-1 카드(85.60 × 53.98 mm) 사각형 검출로 스케일 산출·개인 홍채 지름 캘리브레이션 |
| 3. 채택 프레임 게이팅 | \|yaw\| ≤ 5°, \|pitch\| ≤ 5°, `eyeBlink` < 0.2, 정면 시선, 홍채 지름 ≥ 20 px, 얼굴 화면 중앙 |
| 4. 통계 처리 | 채택 프레임 30~60개 중앙값, IQR 밖 제거, 신뢰구간 병기 |
| 5. 원용/근용 보정 | 홍채 크기로 추정한 거리로 원용 PD 환산값 병기 |
| 6. 단안 PD | 코 중심선(168/6/197)에서 좌/우 홍채 중심까지 거리 |
| 7. 출력 | `pd_far`, `pd_near`, `pd_mono_left/right`, `confidence`, `sample_count`, 조건 로그. "참고용 — 검안·조제용 아님" 고정 노출 |

**오차 예산(PD 63 mm 기준)**: 홍채 지름 개인차 ±0.5 mm → ±2.7 mm(최대 요인), 홍채–동공 편심 0.5~1 mm, 랜드마크 노이즈 ±1 px, yaw 5°에서 0.3 mm 미만, 광각 왜곡 수 %.

**검증 방법**: 피험자 20명 이상, 동공거리계/안경원 기준값. MAE, Bland-Altman, 반복성(5회), 조명 3 × 거리 3 편차.

## 4. PoC 시스템 구성
```
Camera Layer      getUserMedia → <video>(mirrored) → 프레임 콜백
Tracking Core     MediaPipe FaceLandmarker (WASM + GPU) → landmarks[478], matrix[4×4], blendshapes[52]
Fitting Core ★    앵커/스케일 솔버 · One-Euro 필터 · 상태기계 · PD 추정기 — DOM/WebGL 의존 없는 순수 함수(공용 코어, TS)
Render Layer      Three.js: 비디오 배경 · 얼굴/머리 오클루더 · 안경 GLB(실치수) · 카메라 파라미터 정합
Debug / QA HUD    랜드마크 오버레이 · 지터/지연/FPS 계기 · 세션 녹화·재생 · 지표 CSV 내보내기
Product Adapter   제품 마스터 JSON(mock) → 프레임 스펙·GLB·앵커 메타
```
**공용 코어 설계 원칙**: 입력은 랜드마크·행렬 배열, 출력은 포즈·스케일·PD 결과인 순수 함수. 녹화 랜드마크 시퀀스와 기대 출력을 **골든 테스트 벡터(JSON)**로 남기고, 안드로이드 Kotlin 코어는 같은 벡터를 허용 오차 내로 재현해야 통과.

## 5. 기술 스택
TypeScript + Vite, `@mediapipe/tasks-vision` FaceLandmarker(float16, GPU delegate, numFaces=1), Three.js(WebGL2) + GLTFLoader, One-Euro 필터 자체 구현, OpenCV.js(카드 검출에만), 자체 HUD·녹화/재생. 대상: Chrome(Android/데스크톱), Safari(iOS 17+).

## 6. 검증 계획 — 지표와 판정 기준
**① 위치**: 브릿지 착지 오차 ≤ 2 mm(조건부 4), 힌지 위치 오차 ≤ 3 mm(5), 프레임 폭 비율 오차 ≤ 3 %(6), 코 관통·부유 0 %/≤ 5 %, 오클루전 오류 ≤ 5 %, 주관 평가 ≥ 4.0/5.
**② 추종**: 정지 지터 ≤ 0.5 px / ≤ 0.3°, 모션 지연 ≤ 50 ms, 추적 유지율 ≥ 95 %, 재획득 ≤ 300 ms, 렌더 FPS ≥ 24/30/24, 파이프라인 지연 ≤ 80 ms.
**③ PD**: MAE ≤ 2.0 mm, Bland-Altman ±3 mm, 반복성 ≤ 1.0 mm, 조건 민감도 ≤ 1.5 mm, 성공률 ≥ 90 %.
시험 조건: 조명 3(300 lx/50 lx/역광) × 거리 3(30/45/60 cm) × 포즈(정면, yaw ±15/30/45°, pitch ±15/30°, roll ±15/30°, 손 가림), 피험자 20명+, 프레임 3종.
절차: W1 녹화 세트 구축 → W4 실시간 세션 → W3~W4 PD 기준값 수집.

## 10. Go/No-Go 판정과 대안 경로

## 11. 구현 결정 사항 (설계 확정)

기획서가 "W1에서 실측으로 확정"으로 남긴 항목과 구현에 필요한 세부 결정이다. 런타임 디버그 토글로 실측 검증할 수 있게 한다.

### 11.1 좌표계·단위
- **씬 단위는 mm.** MediaPipe 행렬은 cm 단위이므로 코어에서 이동 성분(translation)을 ×10 하여 mm 행렬로 변환한다. 정규 얼굴 모델 정점도 ×10.
- **카메라 공간**: MediaPipe 기하 파이프라인과 동일하게 원점 = 카메라, +X 우, +Y 상, −Z 전방(얼굴은 z < 0). Three.js `PerspectiveCamera(fovY=63°, aspect=영상 비율, near=10 mm, far=100 000 mm)`를 원점에 둔다.
- **행렬 패킹**: `Matrix.data`는 열 우선(column-major)으로 가정하고 Three.js `Matrix4.fromArray`에 직접 넣는다. HUD에 전치 토글을 두어 W1에서 검증한다(이동 성분 z가 −200 ~ −1200 mm 범위면 정상).
- **미러링**: 비디오·랜드마크 오버레이·WebGL 캔버스를 하나의 컨테이너에 넣고 CSS `scaleX(-1)`을 컨테이너에 한 번만 적용한다. 텍스트 HUD는 컨테이너 밖 별도 레이어. 3D 씬 자체는 미러링하지 않으므로 좌/우 랜드마크 인덱스는 이미지 좌표 기준 그대로다(127 = 이미지 좌측 = 피험자의 우측 관자놀이).
- **메트릭 랜드마크 복원**: 얼굴 오클루더와 Kabsch 대안 경로는 정규화 랜드마크(x, y, z)를 카메라 공간으로 역투영해 얻는다. 깊이는 행렬 이동 성분 z를 기준으로 하고 랜드마크 상대 z를 영상 폭 기준 mm로 환산한다. 화면 x, y는 정확히 일치하므로 실루엣 기반 오클루전에 적합하다.

### 11.2 안경 리깅
- GLB 원점 = 브릿지 중심(코 접점), +Y 위, +Z 얼굴 정면(정규 모델과 동일 방향). 다리는 −Z 방향으로 뻗는다.
- 정규 모델 기준 브릿지 착지점 `P_bridge = midpoint(168, 6)` 을 기본 앵커로 하고, 코 착지 보정으로 Z(전방) 오프셋을 더한다.
- 안경 노드 행렬 = `FaceMatrix(mm) · T(P_bridge + noseOffset) · S(sx, 1, 1)` (`sx` = 사용자 폭 보정 비율, 실치수 모드에서는 1).
- GLB 로드 실패 시 스펙(렌즈 폭·브릿지·다리 길이·렌즈 높이·형태)으로 **절차적 안경**을 생성해 동일 노드 규격으로 사용한다. 3종 샘플 GLB는 스크립트로 생성해 `public/assets/frames/`에 둔다.

### 11.3 공용 코어 인터페이스
- 입력 `FrameInput { timestampMs, imageWidth, imageHeight, landmarks: {x,y,z}[478] | null, matrix: number[16] | null, blendshapes: Record<string, number> | null }`
- 출력 `FitOutput { state, glassesMatrix(mm, column-major), rawFaceMatrix, filteredFaceMatrix, faceMetricPoints(Float32Array 478×3, mm), widthScale, angles{yaw,pitch,roll}, pd: PdEstimate | null, alpha }`
- 코어는 `three`·DOM에 의존하지 않는다. 자체 `vec3/quat/mat4` 최소 구현을 사용한다.
- 골든 벡터 파일 형식: `{ version, camera{fovY, aspect}, frames: FrameInput[], expected: {glassesMatrix, state, pd?}[] , tolerance }`.

### 11.4 필터·상태기계 기본값
- One-Euro: 위치 `minCutoff=1.0 Hz, beta=0.02, dCutoff=1.0`; 회전 `minCutoff=1.0, beta=0.5`; 스케일 `minCutoff=0.5, beta=0`. HUD 슬라이더로 조정.
- 상태기계: `Tracking`(신뢰도 ≥ 0.6 · 각도 범위 내), `Degraded`(범위 밖 또는 신뢰도 0.3~0.6, 필터 강도 2배), `Lost`(미검출). Lost 진입 후 12프레임 유지 → 300 ms 페이드아웃. 재획득은 연속 3프레임 Tracking 조건 충족 시(히스테리시스).
- 신뢰도 근사: 검출 유무 + 얼굴 크기(관자놀이 폭 px ≥ 60) + 각도 범위. MediaPipe Tasks JS는 얼굴 단위 confidence를 제공하지 않으므로 이 근사를 사용한다.

### 11.5 PD 파이프라인
- 홍채 지름 = 좌우 홍채 윤곽 수평 두 점(469↔471, 474↔476) 거리와 수직 두 점의 평균을 px로 계산, 양안 평균. 기본 홍채 지름 상수 11.7 mm(설정 가능).
- 홍채 최소 크기 게이트는 12 px로 둔다. 가상 카메라(수직 FOV 63°)와 720p 입력에서 홍채 11.7 mm는 50 cm에서 약 15 px이므로 기획서의 20 px는 34 cm 이내에서만 만족한다. 입력 해상도를 1080p로 올리면 같은 거리에서 약 22 px가 된다.
- 근용→원용 환산: 카메라 거리 `d = f_px · 11.7 / iris_px`(`f_px = imageHeight / (2·tan(31.5°))`), 안구 회전 중심 거리 13 mm 가정, `pd_far = pd_near · (d + 13) / d`.
- 카드 기준 캘리브레이션은 OpenCV.js 의존을 피하기 위해 PoC에서는 **수동 입력**(카드 폭 px를 HUD에서 드래그 측정)으로 구현하고, 자동 검출은 본 개발 항목으로 둔다.

### 11.6 계측
- 지터: 최근 90프레임(3초 @30 fps) 브릿지 앵커 투영 좌표(px, 720p 환산)와 yaw/pitch/roll의 표준편차.
- 지연: 원본 대비 필터 출력의 상호상관 최대 지연(프레임 → ms).
- FPS·파이프라인 지연: 캡처 타임스탬프 → 렌더 완료 시각.
- 세션 녹화: `FrameInput[]` JSON. 재생 모드는 카메라 없이 녹화 타임스탬프로 코어를 구동한다. CSV 내보내기는 프레임별 지표.
